# HotelHub — Документация архитектуры проекта

Методическое пособие для преподавателя. Документ описывает **все слои**
клиент-серверной архитектуры и **назначение каждого файла**: зачем он нужен
и что делает. Подходит для объяснения студентам «сверху вниз» — от браузера
до базы данных.

Проект: учебный сервис поиска и бронирования отелей на **Django 6.0.5**,
построенный по паттерну **MVT (Model – View – Template)**.

---

## 1. Общая картина: четыре слоя

Запрос пользователя проходит сверху вниз, ответ возвращается снизу вверх.

```
┌───────────────────────────────────────────────────────────────┐
│ 1. КЛИЕНТСКИЙ СЛОЙ — браузер                                    │
│    HTML-шаблоны + static (CSS/JS). Отправляет GET/POST-запросы. │
└───────────────────────────────┬───────────────────────────────┘
                                 │  URL-запрос
┌───────────────────────────────▼───────────────────────────────┐
│ 2. СЛОЙ МАРШРУТИЗАЦИИ — config/                                 │
│    urls.py направляет запрос в нужное приложение.               │
│    settings.py хранит всю конфигурацию проекта.                 │
└───────────────────────────────┬───────────────────────────────┘
                                 │
┌───────────────────────────────▼───────────────────────────────┐
│ 3. СЕРВЕРНЫЙ СЛОЙ — Django-приложения (паттерн MVT)             │
│    core · users · hotels · rooms · bookings                     │
│    Каждое приложение: urls → views → models + templates/static  │
└───────────────────────────────┬───────────────────────────────┘
                                 │  ORM
┌───────────────────────────────▼───────────────────────────────┐
│ 4. СЛОЙ ДАННЫХ — база данных (SQLite / PostgreSQL)             │
│    Models через Django ORM хранят и читают данные.              │
└───────────────────────────────────────────────────────────────┘
```

**Ключевая идея для студентов:** стрелки вниз — это поток запроса
(браузер → маршрутизация → view → модель → БД), стрелка вверх — ответ
(данные из БД → view → шаблон → готовый HTML → браузер).

---

## 2. Паттерн MVT (Model – View – Template)

Django реализует не классический MVC, а его разновидность — **MVT**:

| Компонент | Файл | Роль | Аналогия в MVC |
|-----------|------|------|----------------|
| **Model** | `models.py` | Структура данных, работа с БД через ORM | Model |
| **View** | `views.py` | Логика обработки запроса, «контроллер» | Controller |
| **Template** | `templates/*.html` | Представление, вёрстка ответа | View |

Поток одного запроса: **URL → `urls.py` → `views.py` → `models.py` (ORM) →
`views.py` → `template.html` → HTML-ответ в браузер.**

## 3. Слой маршрутизации и конфигурации — `config/`

Папка `config/` — «мозг» проекта. Здесь нет бизнес-логики, только настройки
и корневая маршрутизация.

| Файл | Зачем нужен |
|------|-------------|
| `config/settings.py` | Главный файл конфигурации. Перечисляет установленные приложения (`INSTALLED_APPS`), middleware, где искать шаблоны и статику, параметры базы данных, локализацию, а также подключает кастомную модель пользователя (`AUTH_USER_MODEL = 'users.User'`) и адреса входа/выхода. |
| `config/urls.py` | Корневой «диспетчер» адресов. По началу URL передаёт запрос в нужное приложение через `include()` (`/hotels/` → `hotels.urls`, `/users/` → `users.urls` и т.д.). В режиме `DEBUG` отдаёт медиафайлы. |
| `config/wsgi.py` | Точка входа для **синхронных** production-серверов (Gunicorn, uWSGI). Экспортирует объект `application`. |
| `config/asgi.py` | Точка входа для **асинхронных** серверов (Uvicorn, Daphne). Нужен для async/WebSocket-нагрузок. |
| `config/__init__.py` | Помечает папку как Python-пакет. Пустой. |

**Важно про `settings.py`:**
- `INSTALLED_APPS` — если приложения нет в этом списке, Django его «не видит»:
  не найдёт модели, миграции и шаблоны.
- `AUTH_USER_MODEL = 'users.User'` — задаётся **в самом начале проекта**,
  переопределяет стандартного пользователя Django на наш кастомный.
- `ALLOWED_HOSTS` — список доменов, которым разрешено обслуживать сайт.
- `LOGIN_URL`, `LOGIN_REDIRECT_URL`, `LOGOUT_REDIRECT_URL` — куда вести гостя
  с закрытой страницы и куда отправлять после входа/выхода.

## 4. Клиентский слой — глобальные шаблоны и статика

### 4.1. Глобальные шаблоны — `templates/`

Общий «каркас» страниц. Все страницы приложений наследуются от `base.html`.

| Файл | Зачем нужен |
|------|-------------|
| `templates/base.html` | Базовый шаблон-каркас: `<head>`, подключение `base.css` и `main.js`, блоки навигации, футера, вывод flash-сообщений и «дырки» (`{% block %}`), которые заполняют дочерние шаблоны. |
| `templates/includes/navbar.html` | Верхняя навигация. Меню справа меняется в зависимости от того, вошёл пользователь или нет (`{% if user.is_authenticated %}`). Подсветка активного пункта делается на сервере через `request.resolver_match`. |
| `templates/includes/footer.html` | Подвал сайта с годом (`{% now "Y" %}`). |

### 4.2. Глобальная статика — `static/`

| Файл/папка | Зачем нужен |
|------------|-------------|
| `static/css/base.css` | Дизайн-система проекта: CSS-переменные, сетка карточек, формы, кнопки, бейджи. Подключается в `base.html`. |
| `static/js/main.js` | Общий JavaScript всех страниц: автофокус на поле поиска, мягкое появление карточек. |
| `static/img/`, `static/fonts/` | Папки под глобальные изображения и шрифты. |

> **Термин для студентов:** статика (`static`) — это файлы, которые не
> меняются на лету (CSS, JS, картинки). Медиа (`media`) — файлы, которые
> **загружают пользователи** (например, аватары).

## 5. Серверный слой — Django-приложения

Проект разбит на **5 приложений**. Каждое отвечает за свою зону и изолировано:
свои `models`, `views`, `urls`, шаблоны и пространство имён URL.

### Типовая структура одного приложения

```
<app>/
├── __init__.py        — помечает папку как пакет Python
├── apps.py            — конфигурация приложения (имя, verbose_name)
├── urls.py            — маршруты приложения (app_name + urlpatterns)
├── views.py           — контроллеры: обработка запроса, логика
├── models.py          — структура данных (таблицы БД через ORM)
├── forms.py           — формы (если есть ввод данных пользователем)
├── admin.py           — регистрация моделей в админ-панели /admin
├── tests.py           — автотесты приложения
├── migrations/        — история изменений схемы БД
├── templates/<app>/   — HTML-шаблоны приложения
└── static/<app>/      — CSS/JS/img приложения
```

### 5.1. `core` — ядро и главная страница

«Объединяющее» приложение. **Своих данных не хранит** — собирает витрину из
других приложений.

| Файл | Зачем нужен |
|------|-------------|
| `core/views.py` | View `home()` — главная страница. Берёт топ-отели по рейтингу, свободные номера и статистику, отдаёт в шаблон. **Прокомментирован построчно.** |
| `core/urls.py` | Единственный маршрут: пустой адрес `''` (корень сайта) → `views.home`. |
| `core/models.py` | Пустой — у core нет своих таблиц (намеренно, как ориентир). |
| `core/admin.py` | Пустой — регистрировать нечего. |
| `core/apps.py` | Конфигурация приложения `CoreConfig`. |
| `core/templates/core/home.html` | Витрина: «геройный» баннер, статистика, карточки популярных отелей и свободных номеров. |
| `core/management/commands/seed.py` | **Команда наполнения БД** демо-данными: `python manage.py seed`. Создаёт отели, номера, пользователя `guest`, суперпользователя `admin` и демо-брони. Использует `get_or_create`, чтобы повторный запуск не плодил дубли. |

### 5.2. `users` — пользователи и аутентификация

Отвечает за регистрацию, вход, выход и личный кабинет. Реализует **сервисный
слой аутентификации**.

| Файл | Зачем нужен |
|------|-------------|
| `users/models.py` | Кастомная модель `User` — наследник `AbstractUser`. Сохраняет весь механизм Django (хэширование паролей, права) и **добавляет** поля `phone` и `avatar`. Подключается через `AUTH_USER_MODEL`. |
| `users/forms.py` | `UserRegisterForm` — наследник `UserCreationForm`. Добавляет к стандартной регистрации поля `email` и `phone`. |
| `users/views.py` | Три сервиса + кабинет: `register_view` (регистрация + мгновенный вход), `login_view` (вход через `authenticate`/`login`), `logout_view` (выход через `logout`), `profile_view` (кабинет, защищён `@login_required`). |
| `users/urls.py` | Маршруты: `register/`, `login/`, `logout/`, `profile/`. Пространство имён `users:`. |
| `users/admin.py` | `CustomUserAdmin` — наследник `UserAdmin`, добавляет `phone`/`avatar` в админку. |
| `users/templates/users/login.html` | Форма входа. |
| `users/templates/users/register.html` | Форма регистрации с подсказками и ошибками полей. |
| `users/templates/users/profile.html` | Личный кабинет: данные пользователя + его бронирования. |

**Проверка сервисного слоя (регистрация / вход / выход):**
- Регистрация: `POST /users/register/` создаёт пользователя, хэширует пароль
  через `form.save()` и сразу логинит (`login(request, user)`).
- Вход: `POST /users/login/` — `authenticate()` проверяет пару логин/пароль,
  `login()` кладёт пользователя в сессию. Поддерживает `?next=` для возврата.
- Выход: `GET /users/logout/` — `logout()` очищает сессию, редирект на главную.

### 5.4. `rooms` — номера

| Файл | Зачем нужен |
|------|-------------|
| `rooms/models.py` | Модель `Room`: **внешний ключ на `Hotel`** (`related_name='rooms'`), номер, тип (choices: single/double/suite/family), цена за ночь, вместимость, доступность. |
| `rooms/views.py` | `room_list` — поиск через ORM по названию отеля **или** типу номера (объединение условий через `Q(...) | Q(...)`); `room_detail` — страница номера с кнопкой брони. |
| `rooms/urls.py` | Маршруты: `''` (список), `<int:pk>/` (детально). Пространство `rooms:`. |
| `rooms/admin.py` | `RoomAdmin`: колонки, фильтры по типу/доступности/отелю, поиск. |
| `rooms/templates/rooms/list.html` | Список номеров + форма поиска. |
| `rooms/templates/rooms/detail.html` | Страница номера. Кнопка «Забронировать» для вошедших; гостю — «Войдите, чтобы забронировать» с `?next=`. |
| `rooms/templates/rooms/_card.html` | Карточка номера с бейджем «Свободен/Занят». |
| `rooms/static/rooms/css/style.css` | Стили темы номеров. |

**Связь для студентов:** `Room` ссылается на `Hotel` через `ForeignKey`.
Это связь «один-ко-многим»: у одного отеля много номеров. Доступ обратно —
`hotel.rooms.all()`.

### 5.5. `bookings` — бронирования

Ядро бизнес-логики: связывает **пользователя**, **номер** и **даты**.

| Файл | Зачем нужен |
|------|-------------|
| `bookings/models.py` | Модель `Booking`: FK на пользователя (`settings.AUTH_USER_MODEL`) и на `Room`, даты заезда/выезда, число гостей, статус (pending/confirmed/cancelled). Свойства `nights` и `total_price` считаются на лету. |
| `bookings/forms.py` | `BookingForm` (ModelForm): поле `room` скрыто, пользователь вводит даты и гостей. Метод `clean()` проверяет, что выезд позже заезда. |
| `bookings/views.py` | `booking_list` (свои брони), `booking_create` (создание брони на номер, привязка к `request.user`), `booking_cancel` (смена статуса на «отменено» без удаления записи). Все три защищены `@login_required`. |
| `bookings/urls.py` | Маршруты: `''` (список), `create/<int:room_id>/`, `cancel/<int:pk>/`. Пространство `bookings:`. |
| `bookings/admin.py` | `BookingAdmin`: колонки, фильтры по статусу/датам, поиск, `date_hierarchy`. |
| `bookings/templates/bookings/create.html` | Форма бронирования с итоговой сводкой по номеру. |
| `bookings/templates/bookings/list.html` | Список броней с кнопкой отмены. |
| `bookings/migrations/` | Две миграции: `0001` создаёт таблицу, `0002` добавляет FK на пользователя. |

**Полный цикл бронирования:**
1. Пользователь на странице номера жмёт «Забронировать» → `bookings/create/<room_id>/`.
2. `booking_create` показывает форму, при `POST` привязывает бронь к
   `request.user` и сохраняет.
3. Бронь появляется в «Мои брони» и в личном кабинете.
4. Стоимость = `price_per_night × nights` (свойство `total_price`, в БД не хранится).
5. Отмена меняет статус на `cancelled`, запись остаётся (сохраняется история).

## 6. Слой данных — база и ORM

| Понятие | Объяснение |
|---------|------------|
| **ORM** | Object-Relational Mapping. Позволяет работать с БД через Python-объекты вместо SQL: `Hotel.objects.filter(city='Астана')` вместо `SELECT ... WHERE ...`. |
| **Модель** | Класс-наследник `models.Model`. Один класс = одна таблица, одно поле = одна колонка. |
| **Миграции** | Файлы в `migrations/` — история изменений схемы БД. Создаются `makemigrations`, применяются `migrate`. |
| **`db.sqlite3`** | Файл базы данных (для учебного проекта — SQLite). В продакшене заменяется на PostgreSQL сменой `DATABASES` в `settings.py`. |

**Связи между таблицами в проекте:**

```
User (users)                Hotel (hotels)
  │ 1                          │ 1
  │                            │
  │ M                          │ M
Booking (bookings) ──M──1── Room (rooms)
```

- Отель → номера: один-ко-многим (`Room.hotel`).
- Пользователь → брони: один-ко-многим (`Booking.user`).
- Номер → брони: один-ко-многим (`Booking.room`).

## 8. Как запустить проект

```bash
# 1. Виртуальное окружение
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

# 2. Зависимости
pip install -r requirements.txt

# 3. Миграции (создание таблиц)
python manage.py migrate

# 4. Наполнение демо-данными
python manage.py seed

# 5. Запуск сервера разработки
python manage.py runserver
```

Далее в браузере: **http://127.0.0.1:8000/**

**Демо-доступы после `seed`:**
- Обычный пользователь: `guest` / `guestpass123`
- Администратор (для `/admin`): `admin` / `admin12345`

- [ ] Главная (`/`) показывает отели, номера и статистику.
- [ ] Поиск отелей по городу (`/hotels/?city=Астана`) работает.
- [ ] Поиск номеров по типу/отелю (`/rooms/?q=люкс`) работает.
- [ ] Регистрация создаёт пользователя и сразу логинит.
- [ ] Вход и выход работают, сессия сохраняется.
- [ ] Личный кабинет (`/users/profile/`) доступен только вошедшим.
- [ ] Бронирование номера создаёт запись, привязанную к пользователю.
- [ ] Даты проверяются: выезд не может быть раньше заезда.
- [ ] Отмена брони меняет статус, не удаляя запись.
- [ ] Админка (`/admin`) даёт управлять всеми сущностями.

Все пункты проверены на Django 6.0.5 — система запускается и работает.
